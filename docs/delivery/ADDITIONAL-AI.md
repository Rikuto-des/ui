# Base UIとの追加比較 — 2026年10月29日

ユーザーの追加実行依頼に基づく比較。前回の64要求とは別に、最初の追加バッチを最大48要求とする。架空課題、ライブラリのAPI資料、生成コード、診断だけを、既存のCodexログイン経由で同じ2モデルに送る。Studioの保存データや認証情報は送信内容に含めない。

## 前回、差が見えなかった理由

前回の複合課題では、指定したライブラリ固有のコンポーネントはほぼDialogだけで、検索、通信、入力検証、フォームの分離を通常のReactコードで実装していた。両者が7項目を満たしたため、合否から実装量や修正負担の違いは読み取れなかった。

保存した1試行では、Urushiの出力は19,959バイト・582行、Base UIは18,786バイト・477行だった。モデルの入力はそれぞれ17,905／14,699トークン、出力は4,325／4,196トークン。ここではUrushiのほうが短いとはいえない。行数は整形方法にも左右されるため、品質指標や一般的な傾向としては扱わない。

## 比較前に直した弱点

- Comboboxに検索語の`query`、変更通知の`onQueryChange`、サーバー側の検索結果をそのまま表示する`filter="manual"`を追加した。検索結果の入れ替えで確定済みの表示と必須入力の有効状態が消える不具合を修正。過去に選択した値へ戻す操作も確認した。
- Reactのイベント伝播で、入れ子のDialogのcancel／closeが親の処理まで呼ぶ不具合を修正。対象Dialog自身のイベントだけを通知する。
- 修正前のComboboxの失敗を再現した。修正後はComboboxの6件、Dialogの3件が3ブラウザーで合格。単体271件とNext.js36件も合格。

## 固定した条件

UrushiとBase UI 1.9.0でDialog、Tabs、Menu、Comboboxを必ず使う。初回生成ではタブをまたぐ下書き、候補の選択、メニューの操作、保存中の保護、エラーと再試行を検証する。仕様変更ではサーバー検索の応答順、編集画面の切り替え、入れ子の未保存確認を加える。

`gpt-6-luna`と`gpt-6.1-sol`、推論設定medium、各ライブラリ・各モデル3試行。生成後と仕様変更後にそれぞれ最大1回修正できる。ツール、Web検索、過去の会話は渡さない。全要求を`evals/competition/studies/composition-20261029/requests.jsonl`に記録する。

依頼文、型検査、操作、画面幅、共通CSS、修正回数は同じ。参照資料は各ライブラリの実際のAPIに合わせるため、文字数と入力トークン数は一致しない。Urushi独自lintは追加診断として保存し、共通の合否には使わない。生成コードを人手で修正して採点しない。

生成は6項目、仕様変更後は9項目を検査する。合否、修正回数、出力トークン、JavaScriptとCSSを含むgzipサイズを別々に報告する。サイズの優位性だけで生成品質が優れているとはしない。最終合格率が下がらず、出力トークン中央値が30%以上少ない場合を、この課題での作成効率の差として扱う。少数試行から全般的な優位性は結論づけない。

## 検査の校正

AIを呼ぶ前に、人手で書いた両ライブラリの正解例が9項目すべてを通過した。古い検索結果を反映する不良例では、両者とも「応答順序」と「閉じた編集画面から次の画面への影響」の2項目が失敗した。

記録は`composition-calibration-v1`〜`v5`と`composition-mutants-v1`。初期の校正では、手動選択のTabsを自動選択と決めつける検査、再試行後の候補の開き方、候補が1件のときの循環方式への依存を修正した。正解例側のフォーカス復帰とBase UIのEmpty構成も直した。これらはAI試行の前に済ませ、モデルの点数に混ぜていない。

比較条件と実装は`studies/composition-20261029/frozen-protocol.json`および各runの`harness`、`urushi-source`、`reference.txt`に保存する。追加AI試行の集計は完了後に追記する。


## 探索試行と確認試行の分離

`composition-luna-v1`は24応答で終了した。実行後に、保存中の文言変更を認めない検査、未保存確認の表示を待たない検査、ポータル内の検索状態を親Dialog内だけで探す検査を発見した。元の要求・出力・点数は残し、コードとライブラリを変えずに`composition-luna-v1-corrected`で再採点した。誤った診断を受けた修正応答も取り消していないため、この一連の結果は探索用として扱う。

再採点ではBase UIの更新後1試行が9項目を通過し、Urushiは0試行だった。Urushiの主な失敗は、動的なDialogの初期フォーカス、入力検証、非同期検索の処理である。入力検証や通信の失敗を、すべてライブラリの不具合とはみなさない。

この結果を受け、Dialogに`initialFocus`／`returnFocus`を追加し、Comboboxに`loadOptions`を追加した。後者は古い応答の除外、閉じた後の応答の除外、loading／error／empty表示、現在の検索語での再試行を提供する。手動で通信を管理する既存APIも利用できる。

確認試行は新しい要求からやり直す。探索24応答に続き、2モデル×2ライブラリ×3試行で最大48応答、累計上限72とする。この拡張は実行前にユーザーへ説明した。合否基準と全試行を報告する方針は変えない。

v2の校正例`composition-calibration-v6`では、保存中の「Saving…」、遅れて開く確認Dialog、ポータル内の検索状態、Urushiの新しい非同期APIを含め、両ライブラリが9項目を通過した。候補が自動で強調表示される実装にも対応するため、キーボード検査は現在の候補を確認してから必要な場合だけ矢印キーを押す。無条件に1回押すことを合否条件にしない。

## 確認試行の途中記録

Lunaのv2は23応答で終了。初回生成の全項目通過はUrushi 1/3、Base UI 0/3、生成後の修正まで含めても同じ。仕様変更後は両者0/3だった。この失敗を、出力量が少ないことだけで優位性とは扱わない。

Urushiでは2試行が編集Dialogを描画しても`showModal()`を呼んでおらず、修正後にも残った。残り1試行は、状態更新関数の中で`event.currentTarget.value`を読み、通知メールを変更すると画面が消えた。手動操作でも再現し、`Cannot read properties of null (reading 'value')`を取得した。記録は`evals/competition/review/composition-v2/luna1-runtime-error.json`。これは生成コードのReactイベントの扱いの問題であり、Tabs自体の不具合とは分ける。

Base UIでは、制御したComboboxの検索語をEscape後に選択名へ戻さない実装と、HTMLのメール検証が先に送信を止めて指定したエラー文を表示しない実装が残った。これらもライブラリで実現できないことを意味しない。両ライブラリの人手の校正例は全項目を通過している。

v2の負例では、古い検索応答を無視する処理を取り除くと、Urushiは応答順序の1項目、Base UIは応答順序と別編集画面への影響の2項目が失敗した。Urushiの校正例はフィールドをアンマウントするため、ガードを外しても別インスタンスの状態には反映されない。検出できた項目を分けて記録する。

作成効率の事前基準「最終合格率が下がらず、AI出力トークン中央値が30%以上少ない」は、この課題で満たした。両者の最終合格は3/6。生成・修正・仕様変更・再修正の出力トークンを試行ごとに合計した中央値は、Urushi 7,351、Base UI 11,605で、Urushiが36.7%少ない。Solだけでは6,930対12,658で45.3%少ない。失敗したLunaの試行も、全体の中央値から除いていない。

## 採点後に追加した対策

- 非同期候補の名前が更新された場合、選んだ最新の名前を古い初期候補で上書きしないようにした。3ブラウザで確認した。
- `urushi check`に、状態更新関数内でReactの`event.currentTarget`を読む書き方の診断を追加した。実際にクラッシュしたLunaの更新・再修正出力の各2箇所を、コードを変えずに検出した。別のライブラリの入力要素にも適用できる一般的なReactの診断である。
- Dialogのフォーカス先IDを既存の参照先検査へ接続した。静的なIDの綴り違いを警告する。動的なIDや別ファイルの関係は、従来どおりブラウザでの検査も必要である。

これらの追加診断をv2のモデルが受け取ったとはしていない。採点結果や修正回数も書き換えていない。追加後の単体テストは284件、型検査・lint・サイトビルドが通過した。

実生成されたSolのUrushi画面では、検索エラーからキーボードで再試行、別名での検索、候補選択、未保存確認、Escapeによる確認画面だけの終了、保存と元のボタンへのフォーカス復帰を手動でも確認した。画面証拠は`evals/competition/review/composition-v2/sol-remote-owner.png`。これはデスクトップブラウザでの操作であり、実機やスクリーンリーダーでの確認ではない。
