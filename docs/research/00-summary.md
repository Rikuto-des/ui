# 新しい UI ライブラリを作るための調査まとめ（2026-10-22）

8 つの観点で調べた結果（[01](01-shadcn-ui.md)〜[08](08-metrics.md)）を横断して、次の 3 つにまとめる。

- いま何が起きているか
- どこが空いているか
- 何を作るべきか

どの数字・主張にも、元のレポートに出典を付けてある。

> 調査の制約
> - Web 検索は、全体で 200 回の上限に達した。
>   - 後半は、公式ページの直接取得、GitHub / npm / webstatus.dev の API、MDN のブラウザ互換データで補っている。
>   - Reddit と X の投稿は直接確認できていない。
> - npm は 2026-10-13〜15 のデータが欠けている。
>   - 数値は [08-metrics.md](08-metrics.md)（2026-09-28〜10-04 の週）を正とする。

## 1. 結論

1. **shadcn/ui は「コンポーネント集」から「配布の仕組み＋AI が最初に選ぶ選択肢」に変わった。**
   - 数字で見ると:
     - CLI は週 1,336 万 DL。React に対する比率は 2 年で 17 倍。
     - GitHub スターは 12.6 万。レジストリ（配布元）は 479 件ある。
     - Claude Code が UI 部品を勧めるとき、約 9 割は shadcn。
   - 結論: shadcn と同じ土俵で「別のコンポーネント集」として勝負するのは最悪手。
     - **配布の形式は shadcn に合わせて乗る。**
     - **戦う場所は、shadcn が仕組みの上で解けていない問題にする。**
2. **AI が UI ライブラリの一番の利用者になった。**
   - 次の 3 つを同時に満たすライブラリは、まだない。
     - AI が選びやすい
     - AI が壊せない
     - AI が使っても見た目が画一的にならない
   - ここが最大の勝ち筋。
3. **開発者の不満の上位 2 つは、shadcn が部分的にしか対応できていない。**
   - 1 位「どれも同じに見える」: 作者本人が「My bad」と認めている。用意されたスタイル 8 種類では解消していない。
   - 2 位「コピペした後に更新できない」: `update` コマンドがなく、作者は「AI にマージさせればいい」という方針。
4. **技術の土台は、ほぼ決まった。**
   - React 19 以上
   - 部品の中身（ヘッドレス層）: **Base UI**。React Aria も選べるようにする。
   - スタイル: Tailwind v4 と CSS 変数。デザイントークンは **DTCG 2025.10** を正本にする。
   - ブラウザ標準の機能: Popover、anchor positioning、invoker commands を段階的に使う。
   - モーション: CSS と motion。
   - ここで差別化しようとしなくていい。
5. **空白地帯（作る価値がある場所）は 6 つ。**
   - 更新できる「コードの所有」
   - エージェントが破れないデザインのルール
   - 色以外での個性（密度・組版・動き・形）
   - 製品レベルの複雑な部品と状態
   - 1 つの定義から複数の形式へ出力する仕組み
   - 日本語など CJK の組版

## 3. 伸びたもの・止まったものの共通点

### 伸びたもの

| 例 | 伸びた理由 |
|---|---|
| **shadcn** | コードが手元に来る ＋ レジストリで配れる ＋ AI がまず選ぶ。この 3 つが互いを強め合った |
| **React Bits**（2025 年に +32.8k★、JS Rising Stars 総合 2 位） | 部品 1 つがそのまま SNS で映えるデモ動画になる。導入の手間がほぼない。shadcn と競合せず、足りない部分を補う |
| **mapcn**（10 か月で 12.3k★） | 地図という特定分野に絞り、shadcn の流儀に乗った |
| **Base UI** | 信頼できる体制（MUI のチームが複数人で開発、毎月リリース）。そこに shadcn が採用した |
| **json-render / MCP Apps** | オープンな仕様で、AI 時代の新しい需要を取った |
| **StyleX** | 「エージェントが書くコードにも強い、上書きされにくいスタイルのルール」として再評価された |

**共通点**: すでにある流れ（shadcn・AI）に乗りつつ、**1 点だけ明確に尖っている**。

### 止まったもの

| 例 | 止まった理由 |
|---|---|
| MUI / antd / Chakra / Headless UI | スタイル込みの大型パッケージは React に対する比率が半分以下に |
| styled-components / Emotion | 実行時 CSS-in-JS |
| vaul / cmdk | 個人の趣味として作られたものに、多くが依存していた |
| Ark / Zag | 1 つのコードで全フレームワークに対応しようとした |
| OpenAI ChatKit | 1 社の製品に閉じていた |
| JollyUI / Park UI / Tremor / 買収後の Kibo | 更新が止まった |
| Magic UI | 目新しさが切れた（年間スター増 13.2k → 6.6k → 3.0k） |

**共通点**: 依存先が弱い、閉じている、新しさだけで勝負していた、のどれか。

## 5. 避けるべきこと

- **shadcn と同じ土俵で「別のコンポーネント集」を出すこと。** レジストリは 479 件、LP 向けのモーション集はもう飽和している。
- **最初から複数フレームワークを自前で実装すること。** 成績が悪い（Ark/Zag、Mitosis、Material Web、Franken UI）。仕様を移植しやすくしておけば、外部の人が移植してくれる。
- **Radix だけに依存すること**（ほぼ 1 人で開発）。vaul / cmdk / tailwindcss-animate のような止まった依存。cva 1.0 のように長くベータのままのもの。
- **実行時 CSS-in-JS。Chromium でしか動かない機能を必須にすること**（interestfor、if()、reading-flow など）。
- **土台 × スタイル × テンプレートの組み合わせを増やしすぎること。** shadcn はすでに 3 × 8 × 6 で、壊れた例が報告され続けている。
- **ドキュメントへの集客を前提にした収益化**（Tailwind Labs の教訓）。
- **★の数を利用量と取り違えること。** A2UI は 16.8k★ でも利用は伸び悩み、tambo は 11.2k★ でも週 7 千 DL。

## 6. 設計の方向性（3 案）

### 案 A: 「エージェントが壊せないデザインシステム」
> 部品ごとに「部品の契約書」（機械が読める仕様ファイル）を 1 つ持たせ、そこから次のものを全部自動で作る。

**部品の契約書に書くこと**

- props のスキーマ
- バリアント
- 上書きしてよい範囲
- 使う場面と使わない場面
- アクセシビリティの要件

**契約書から作るもの**

- React の部品（Base UI ベース）
- shadcn のレジストリ項目
- SKILL.md / llms.txt / MCP
- **lint ルールと型の制約**（勝手な className や生の色を書くとエラーになり、エラー文には直し方を書く）
- json-render / A2UI のカタログ
- Figma Code Connect
- DTCG トークン

**評価**

- 刺さる課題: #2、#6（＋#1 の土台になる）
- 勝ち筋: shadcn は「コードはあなたのもの」という思想なので、ルールを強く縛る方向には振り切れない。
- 弱み: 仕組みが中心で目に見えにくく、デモ映えしない。shadcn/lint が深まると差が縮む。

### 案 B: 「製品 UI 特化（業務・高密度）」
> SaaS や管理画面の「本番の部品」に絞る。

**作る部品**

- データグリッド（仮想化・列操作）
- スキーマから組み立てるフォーム
- 複数選択とタグ入力
- キーボードで入力できる日付・時刻の欄
- Tree、Stepper、Dropzone、コマンドパレット

**作り方**

- loading / empty / error などの状態をすべて最初から入れる。
- 密度を切り替えられるようにする。
- 動作は npm パッケージとしてテストで保証し、見た目だけをレジストリでコピーさせる。

**評価**

- 刺さる課題: #4、#5、#7
- 勝ち筋: 実際に使われる量が大きい（react-hook-form 週 7,000 万、TanStack Table 週 2,660 万）。shadcn は思想上ここに踏み込まない。
- 弱み: 作るのが重い（データグリッドだけで大仕事）。Untitled UI、HeroUI、MUI X と競合する。

### 案 C: 「デザイン言語エンジン（スタイルパック）」
> 色だけでなく「形・密度・組版・モーションの性格」をまとめて 1 つのデザイン言語として切り替える。

**中身**

- 互いにはっきり違うパックを、人間がデザインして少数精鋭で出す。
  - 例: 高密度の業務向け／やわらかい消費者向け／組版重視の編集向け／**和文組版**
- 部品のコードには意味のあるクラス名だけを書く。見た目は CSS とコンテナの style query で丸ごと差し替える。
- AI 向けに「パックのルールを書いた Skill」を付ける。
- 短いコードで共有でき、エージェントが切り替えられる。

**評価**

- 刺さる課題: #1、#9
- 勝ち筋: 不満の 1 位で、デモ映えする（React Bits 型の拡散が狙える）。shadcn と競合せず補える。
- 弱み: 見た目は真似されやすく、目新しさは消える（Magic UI の失速）。デザイン力そのものが問われる。

### 推奨: **A を骨格、C を見せ場、B を中身として後から足す**

組み合わせる理由:

- **C で目を引き、A で使い続けてもらう。**
  - 見た目のパックは入口（デモ・SNS・AI に選ばれるきっかけ）になる。
  - 契約と lint は「エージェントに任せても崩れない」という継続利用の理由になる。
- **C は A がないと成り立たない。**
  - 見た目のパックを安全に差し替えるには、「意味のあるクラス名・トークン・上書きしてよい範囲」が決まっている必要がある。それは A そのもの。
- **B（複雑な部品）は後から足す。**
  - 有料版や拡張として足すと、収益化の柱になる。

**最大のリスク**: shadcn が lint / スタイル / update を急速に充実させていること（月 1 回以上のペース）。

**対策**:

- 配布形式は shadcn 互換にして敵対しない。
- 「契約を最初から全部の土台に置く」設計の深さで差をつける。
- 和文組版のように、shadcn が手を出さない領域を持つ。

## 7. 推奨する技術選定

| 項目 | 選定 | 理由（参照） |
|---|---|---|
| フレームワーク | **React 19 以上のみ**（RSC を前提にし、React Compiler を有効にしてテスト） | 利用率 83.6%。複数フレームワークを自前で持った例は失敗している（[06](06-multi-framework-mobile.md)） |
| 部品の中身（ヘッドレス層） | **Base UI を既定にし、React Aria にも切り替え可能**。部品ごとに付ける `data-slot` や状態の data 属性は自前で持つ | shadcn の既定で、体制が健全。土台を差し替えても使う側が困らないようにする（[02](02-headless-primitives.md)） |
| 部品の組み立て方（API） | compound components ＋ `render` prop。`asChild` は使わない | 業界がそちらに寄っている。Vue Vapor など新しい仕組みでも壊れにくい（[02](02-headless-primitives.md) [06](06-multi-framework-mobile.md)） |
| トークン | **DTCG 2025.10 の JSON を正本**にし、CSS 変数（OKLCH）、Tailwind の `@theme`、Figma 変数へ書き出す | 共通形式が決まった（[04](04-styling-platform.md)） |
| スタイリング | Tailwind v4 ＋ **部品には意味のあるクラス名、見た目は別の CSS**。密度やバリアントは style query で渡す | 見た目のパックの差し替えと、Tailwind の体制リスクへの備え（[04](04-styling-platform.md)） |
| バリアントの組み立て | 小さな自前の関数か tailwind-variants の lite 版。cva 1.0 は避ける | cva は 2 年ベータのまま（[04](04-styling-platform.md)） |
| オーバーレイ | 当面は Base UI の位置計算を使う。位置計算は差し替え可能にしておき、後で anchor positioning に移る。`<dialog>` や popover を既定にはしない | 主要ライブラリも見送っている（アクセシビリティ上の理由）（[02](02-headless-primitives.md)） |
| 段階的強化 | `@supports` で customizable select、corner-shape（スクワークル）、scroll-driven animations を使う | 1〜2 年で効いてくる（[04](04-styling-platform.md)） |
| モーション | CSS（@starting-style、View Transitions、sibling-index()）を基本にし、複雑なものだけ `motion`。**モーションの決まりごとを Skill として同梱する** | Emil Kowalski のルール、framer-motion から motion への移行（[04](04-styling-platform.md) [08](08-metrics.md)） |
| 置き換える依存 | vaul → Base UI の Drawer、cmdk → Base UI の Autocomplete、tailwindcss-animate → tw-animate-css か CSS | 止まった依存を排除する（[02](02-headless-primitives.md)） |
| アイコン | lucide を既定にし、差し替え可能にする（hugeicons、phosphor が急伸中） | [08](08-metrics.md) |
| 配布 | **shadcn レジストリ互換**（`npx shadcn add @名前/button`）＋ 動作部分は npm パッケージ ＋ 将来は更新用の自前 CLI | 一番の入口。両方を組み合わせる形が主流になりつつある（[03](03-ecosystem.md)） |
| AI 向け | 全ページの .md 版、llms.txt、SKILL.md、MCP、**エージェントが読める lint**、部品の契約書 | [05](05-ai-native.md) |
| ライセンス | 中核は MIT。有料パックは商用ライセンス | 採用されやすさと収益化の両立（[03](03-ecosystem.md)） |

## 8. 段階的な進め方（案）

1. **土台づくり**: トークンのスキーマ（DTCG）と部品の契約書のスキーマを決める。契約書から「React の部品・レジストリ JSON・SKILL.md・lint ルール」を書き出す仕組みを作る。
2. **最初に公開するもの（MVP）**
   - 15〜20 個の中核部品
   - はっきり違う見た目のパック 2〜3 個（うち 1 つは和文組版を重視するかは要相談）
   - lint と Skill
   - shadcn CLI で入れられるレジストリ
   - パックを切り替えるとサイト全体の見た目が変わるデモ
3. **拡張**: 更新の仕組み（lockfile と 3-way merge）、複雑な部品（Combobox の複数選択、日付の入力欄、データグリッド、Tree）、状態の標準装備。
4. **AI ネイティブ化**: 生成 UI 向けのカタログ書き出し（json-render、A2UI）、MCP Apps のホストに合わせる表示モード、Figma との同期、有料パック。

## 9. 決めたこと（2026-10-22）

- **方向性**: A＋C。エージェントが破れないデザインのルールを骨格にし、色以外も変えるスタイルパックを見せ場にする。B（複雑な部品）は後から足す。
- **日本語（CJK）の組版**: スタイルパックの 1 つとして持つ。基本は世界向けにし、和文組版に最適化したパックを看板の 1 つにする。
- **収益化**: まずは OSS（MIT）だけで出す。
- **作り方**: すべてスクラッチで作る。Radix・Base UI・Floating UI など外部の UI ライブラリには依存しない。振る舞いはブラウザ標準を土台にして自作する。
- **配布**: 自前の CLI だけで配る。shadcn との互換は持たない。
- **まだ決めていないこと**: 名前、見た目のブランドの方向性、対応ブラウザの下限。

※ 上の §7 にある技術選定表は、方針が決まる前の推奨。「Base UI」と「shadcn レジストリ互換」は採用しないことになった。最新の設計は design ドラフトを正とする。

設計のたたき台は [../design/00-design-draft.md](../design/00-design-draft.md) にある。
